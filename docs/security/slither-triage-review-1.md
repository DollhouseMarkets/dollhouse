False-positive categories applied (per the reviewer's fixed criteria — naming/style, BN254 assembly,
PoolManager-unlock-pattern reentrancy, and design-intended timestamp comparisons):
- `naming-convention` (26): SCREAMING_CASE constants and similar; a style convention, not a
  security issue.
- `assembly` in `contracts/randomness/BN254.sol` only (4 of 9 assembly hits): elliptic-curve
  arithmetic that is expected to use inline assembly. The other 5 assembly hits (all in
  `FamilyHook.sol`, transient-storage and raw-word helpers) are left as needs review — deliberate
  and well-commented on inspection, but not the BN254 case the triage criteria named explicitly.
- `reentrancy-*` on `FamilyHook.sol:357` and `:410` (beforeSwap/afterSwap, both `onlyPoolManager`
  hook callbacks whose external calls run inside the PoolManager's own unlock flow) and on
  `Locker.sol:58` and `:81` (`placeStandardCurve`/`depositBid`, which themselves call
  `poolManager.unlock(...)` — the unlock pattern itself): 4 of 23 reentrancy hits. The remaining 19
  reentrancy hits (RoundManager's randomness-source calls, FeeVault's non-nonReentrant claim/forward
  paths, FamilyFactory.createGenesis) are NOT nonReentrant-guarded and are not PoolManager-unlock
  callbacks themselves, so they are left as needs review rather than assumed safe.
- `timestamp` (38): every hit is a round-phase, sunset, or vesting-cliff comparison against
  `block.timestamp`; this project's mechanism (see `docs/MECHANISM_v3.md`) is deadline-driven by
  design, not a randomness or access-control check that a miner could profitably skew.

No `unused-return` hit (34 total) was marked false positive: the criteria require the ignored
return to be deliberately ignored **with a comment** at the call site, and none of the sampled sites
(mostly ignored tuple fields from `getSlot0`/`modifyLiquidity`, and ignored
`poolManager.unlock(...)`/`settle()` returns) carry such a comment. All 34 are needs review.

No `solc-version`-pragma detector fired in this run (not in the 102-detector output), so that
named false-positive category has no rows to apply to.
