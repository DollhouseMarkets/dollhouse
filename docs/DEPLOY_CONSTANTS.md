Continuation caveats, disclosed:
- A continuation stack's ancestor Fenwick trees start EMPTY at deploy. Entitlements for prior-version links accrue only from the new version's own fees; nothing is migrated, and the prior version's undeployed sleeve stays claimable in the prior version's vault forever.
- **Sunset handover of the $DOLL edge.** A continuation stack adopts the same external genesis token by delegation and has no edge pool of its own, so the 1% edge fee is always *charged* by the ORIGINAL version's hook on that version's own link-one pools. From the moment that version's sunset takes effect (`RoundManager.isSunsetEffective()`), its FeeVault no longer books the protocol share: it transfers the ERC-6909 claim to the successor's FeeVault and calls `accrueForwarded(attribution, amount, hopsLeft)`, which books it with the SUCCESSOR's dev/creator/ancestor/reinforce constants, its own Fenwick sleeve and its own registry (a v1-era index still resolves there by delegation). The hop repeats down a chain of successors (v1 → v2 → v3), bounded at `MAX_FORWARD_HOPS = 8`; `accrueForwarded` accepts only a vault found in the caller's own prior-registry chain. What STAYS in the charging version's vault: the parent-side hop fee and snipe tax for that pool (they reinforce a pool only that version's Locker can add liquidity to), every balance accrued before the handover (dev, creator, sleeve, reinforcement, bond earmark, all still claimable and deployable there), and the whole protocol share again if the hop fails for any reason (a successor that reverts or was never a real deployment is caught and booked locally, so a swap can never fail because of what a later version does). No new privilege is created: the successor is the one the steward already named in the one-shot, 7-day sunset, and the resolved successor vault/router are cached write-once with no setter.
- Attribution across the handover: after the sunset takes effect the prior version's hook also trusts `hookData` from the SUCCESSOR's router (`successor.factory().router()`), so a cross-version route still credits the terminal token's creator; before it takes effect the same route is unattributed and the fee is booked by the prior version's own vault. Trust extends to the IMMEDIATE successor only, with three live versions (v1 sunset to v2, v2 sunset to v3) a route driven by v3's router is unattributed at v1's pools, though the fee itself still forwards all the way to v3.
- A candidate-sentinel attribution is resolved against the candidate list of whichever vault finally BOOKS the fee. While a sunset version's last round is still trading (at most one round past `sunsetAt`), its candidate ids are read by the successor's registry, where they may name a different candidate or none; such a fee is then credited to the wrong candidate's creator or is unattributed. The window is one round long and never recurs, because a sunset version opens no further rounds.

Disclosed risks (pointers):
- The full non-technical disclosure list, including generation-3+ near-free head capture, typical 5–8% parent-value falloff per link, keeper/TWAP-gaming exposure, and the irreversibility and blast radius of the sunset/upgrade switch, is carried in `docs/spec/PROTOCOL_SPEC.md` §R.
- `docs/security/PROPERTY_RESULTS.md` and `docs/security/FORK_RESULTS.md`, measured figures: slot capture ≈0.15% of capital cycled; reinforcement as slow accretion, not a shock absorber; deep-route price-impact degradation; block-1 sniper net profitability on steep curves.

## Round mechanism

These rows SUPERSEDE the "Round timing" row above wherever they differ; the "Threshold H0" row above already reflects the deployed (disabled) value. Every one of them is a hardcoded constant or a constructor parameter fixed at deploy; nobody (steward included) can change any of them afterwards.

| Constant | Value |
|---|---|
| Round duration `D(n)` | `min(15 min × 2^floor((n−1)/2), 12 h)`, a pure function of the ROUND NUMBER and of nothing else (`RoundManager.durationFor(n)`). Rounds 1–2: 15 min; 3–4: 30 min; 5–6: 1 h; 7–8: 2 h; 9–10: 4 h; 11–12: 8 h; 13+: 12 h, capped forever |
| Registration window `R(n)` | `clamp(D(n)/5, 3 min, 1 h)` (`RoundManager.registrationFor(n)`): 3 min / 6 min / 12 min / 24 min / 48 min / 1 h (cap) / 1 h |
| Late entry | Allowed **iff `D(n) ≥ 1 h`**, during the first `D(n)/3` of trading (`RoundManager.lateEntryUntil(n)`: 20 min / 40 min / 80 min / 2 h 40 min / 4 h). A late entrant posts the **same bond**, and **its pool opens the moment it registers**: its own 3-second snipe tax applies from that moment, not from the round's start. There is **no time-based scoring penalty**: see the closing window below. Rounds shorter than an hour refuse a late entrant outright (`RegistrationClosed`) |
| **Scoring window (the CLOSING WINDOW)** | A candidate's score is its average net parent absorption over **`[T_end − W, T_end]`**, where **`W = 15 min` on EVERY round** (`RoundManager.CLOSING_WINDOW_S`, divided by `DURATION_SCALE_DIV`; `RoundManager.closingWindowFor(n)` ignores `n`). It used to widen with the duration (`D(n)/4` above an hour: 2 h → 30 min, 12 h → 3 h); flattened 2026-09-12 so the round number changes only how long a coin has to build support, never the yardstick it is measured with. **The same window for every candidate, whenever it registered**: a late entrant is neither handicapped by a shorter window nor flattered by a longer one, it simply has less time to build the support level the window measures. Because the window measures a LEVEL, support sold back before the bell does not count; and because late entry always closes before the closing window opens, no candidate is ever scored over a span that starts before its own pool did. The threshold `H` is compared against this average exactly as before |
| **Random end** | The round has a public nominal end `T`; nothing swapped after `T` counts. The TRUE end is `T_end = T − (r mod 180 s)`, drawn from a beacon that **did not exist at `T`**. At `T` anyone calls `requestEnd()`, which pins a future drand round; anyone then relays that round's signature to `fulfilEnd(proof)`, which verifies it on chain. Nobody, operator included, can know `T_end` before `T`, so a buy in the last three minutes is a gamble on landing before an end that does not exist yet. `RoundManager.RANDOM_END_S = 180`. The window actually used is `randomEndWindowFor(n) = max(1, min(RANDOM_END_S, D(n) / 4))`: **on mainnet this is always 180 s exactly**, because the shortest round is 15 min and `D(n)/4 >= 225 s`.
