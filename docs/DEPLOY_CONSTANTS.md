Continuation caveats, disclosed:
- A continuation stack's ancestor Fenwick trees start EMPTY at deploy. Entitlements for prior-version links accrue only from the new version's own fees; nothing is migrated, and the prior version's undeployed sleeve stays claimable in the prior version's vault forever.
- **Sunset handover of the ETH edge.** A continuation stack has no ETH-paired pool of its own, so the 1% edge is always *charged* by the ORIGINAL version's hook on the original genesis pool. From the moment that version's sunset takes effect (`RoundManager.isSunsetEffective()`), its FeeVault no longer books the protocol share: it transfers the ERC-6909 claim to the successor's FeeVault and calls `accrueForwarded(attribution, amount, hopsLeft)`, which books it with the SUCCESSOR's dev/creator/ancestor/reinforce constants, its own Fenwick sleeve and its own registry (a v1-era index still resolves there by delegation). The hop repeats down a chain of successors (v1 → v2 → v3), bounded at `MAX_FORWARD_HOPS = 8`; `accrueForwarded` accepts only a vault found in the caller's own prior-registry chain. What STAYS in the charging version's vault: the parent-side hop fee and snipe tax for that pool (they reinforce a pool only that version's Locker can add liquidity to), every balance accrued before the handover (dev, creator, sleeve, reinforcement, bond earmark — all still claimable and deployable there), and the whole protocol share again if the hop fails for any reason (a successor that reverts or was never a real deployment is caught and booked locally, so a swap can never fail because of what a later version does). No new privilege is created: the successor is the one the steward already named in the one-shot, 7-day sunset, and the resolved successor vault/router are cached write-once with no setter.
- Attribution across the handover: after the sunset takes effect the prior version's hook also trusts `hookData` from the SUCCESSOR's router (`successor.factory().router()`), so a cross-version route still credits the terminal token's creator; before it takes effect the same route is unattributed and the fee is booked by the prior version's own vault. Trust extends to the IMMEDIATE successor only — with three live versions (v1 sunset to v2, v2 sunset to v3) a route driven by v3's router is unattributed at v1's pools, though the fee itself still forwards all the way to v3.
- A candidate-sentinel attribution is resolved against the candidate list of whichever vault finally BOOKS the fee. While a sunset version's last round is still trading (at most one round past `sunsetAt`), its candidate ids are read by the successor's registry, where they may name a different candidate or none; such a fee is then credited to the wrong candidate's creator or is unattributed. The window is one round long and never recurs, because a sunset version opens no further rounds.

| **Scoring window (the CLOSING WINDOW)** | A candidate's score is its average net parent absorption over **`[T_end − W, T_end]`**, where **`W = 15 min` on EVERY round** (`RoundManager.CLOSING_WINDOW_S`, divided by `DURATION_SCALE_DIV`; `RoundManager.closingWindowFor(n)` ignores `n`). It used to widen with the duration (`D(n)/4` above an hour: 2 h → 30 min, 12 h → 3 h); flattened 2026-09-12 so the round number changes only how long a coin has to build support, never the yardstick it is measured with. **The same window for every candidate, whenever it registered**: a late entrant is neither handicapped by a shorter window nor flattered by a longer one — it simply has less time to build the support level the window measures. Because the window measures a LEVEL, support sold back before the bell does not count; and because late entry always closes before the closing window opens, no candidate is ever scored over a span that starts before its own pool did. The threshold `H` is compared against this average exactly as before | design decision (2026-09-12) |
| **Random end** | The round has a public nominal end `T`; nothing swapped after `T` counts. The TRUE end is `T_end = T − (r mod 180 s)`, drawn from a beacon that **did not exist at `T`**. At `T` anyone calls `requestEnd()`, which pins a future drand round; anyone then relays that round's signature to `fulfilEnd(proof)`, which verifies it on chain. Nobody, operator included, can know `T_end` before `T`, so a buy in the last three minutes is a gamble on landing before an end that does not exist yet. `RoundManager.RANDOM_END_S = 180`. The window actually used is `randomEndWindowFor(n) = max(1, min(RANDOM_END_S, D(n) / 4))` (review-2): **on mainnet this is always 180 s exactly**, because the shortest round is 15 min and `D(n)/4 >= 225 s`. The quarter-duration clamp binds only on a scaled testnet schedule, where a window comparable to the whole round could put `T_end` at or before `tradingStart`; the `max(1, ...)` keeps the modulus in `fulfilEnd` defined | MECHANISM_v3 §3 |

| `END_TIMEOUT` | **30 min** (`RoundManager.END_TIMEOUT`, a constructor parameter, `END_TIMEOUT_S` env var). | Score checkpoint rings | TWO per pool, off the one accumulator, each written at most once per slot and holding the state immediately BEFORE the first swap of that slot. **Fast:** 36 slots × 5 s = 180 s, exactly the span the random end can land in, so the `T_end` edge resolves to five seconds. **Coarse:** 64 slots × the pool's own `scoreSlotS = ceil((W + 180 s + END_TIMEOUT + 300 s) / 63)`, so the ring reaches back over the whole closing window plus the WHOLE settlement tail. The `END_TIMEOUT` term is review-2b: `fulfilEnd` has no deadline, so a round can be settled as late as `T + END_TIMEOUT` and scored up to `SUBMIT_S` after that, while the far edge of its window is still `T − W − 180 s`. With `W` flat at 15 min and `END_TIMEOUT` 30 min that is `ceil(3180/63) = 51` s on every round, covering 63 x 51 = 3213 s against a requirement of 900 + 180 + 1800 + 300 = 3180 s. The previous sizing (22 s, 1386 s of ring) covered a PROMPT settlement only. Reconstruction is exact between swaps (`R` is constant, so slots with no swap need no entry at all); the only inexactness is a second swap inside the same slot as an edge, where the PRE-swap state is used — which never counts flow LATER than the edge. **The accumulator is never frozen**: it runs forever, as the public measure of a pool's support for the rest of the chain's life | MECHANISM_v3 §1/§3 |
